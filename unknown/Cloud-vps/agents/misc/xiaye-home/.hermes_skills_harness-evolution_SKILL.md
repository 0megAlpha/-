# harness-evolution

## 這個技能存在的理由

DGM／Harness 進化不是「讓模型自己改自己的程式碼」，而是**讓腳手架在真實失敗軌跡上被驗證過的改進所取代**。

三條硬規則（不可協商）：

1. **協同進化，不是模仿**：強模型只修正弱模型「自己失敗的那幾步」，保留其規劃風格。
2. **閘門不可被演化移除**：`TEST_STAGE` / `VERIFY_STAGE` 是硬性要求，演化只能調整
   stages 的**順序與權重**，不能刪掉驗證閘。
3. **樣本不足不升版**：`metrics.trials < 20` 的自評數據一律不採用（防止 LLM 自吹自擂）。

## run_fixes.sh — 每日自動巡檢與修復

**設計原則：先診斷後治療、冪等、可回滾、絕不猜。**

| 修復 | 檢查什麼 | 做什麼 | 是否破壞性 |
|---|---|---|---|
| 01 | `~/.hermes/.env` 的 `API_SERVER_HOST` 是否為 `0.0.0.0` | 備份 → sed → 重啟服務 → curl 驗證 200；失敗則輸出 nginx 反代備案 | 否（有備份可回滾） |
| 02 | 是否還有 >100MB 的檔案卡在 git 追蹤範圍 | 打包到 `/tmp/ai-migration` → sha256 → 僅綁 Tailscale IP 起臨時 HTTP → 寫 `logs/migration.md` | 否（只打包不刪） |
| 03 | `src/` 下是否已有 harness 源碼 | 缺什麼 clone 什麼（`--depth 1`），補 `.gitignore` 雙保險 | 否 |

手動執行：

```bash
bash ~/.hermes/skills/harness-evolution/run_fixes.sh            # 全跑
bash ~/.hermes/skills/harness-evolution/run_fixes.sh --dry-run  # 只診斷不治療
bash ~/.hermes/skills/harness-evolution/run_fixes.sh --only 01  # 只跑單項
```

回滾：

```bash
# 01 的備份會留在這裡
ls -lt ~/.hermes/.env.bak.* | head
cp ~/.hermes/.env.bak.<時間戳> ~/.hermes/.env && systemctl restart hermes-gateway
```

## 掛上 cron（每天 03:00）

```bash
bash ~/.hermes/skills/harness-evolution/install_cron.sh
crontab -l | grep harness-evolution   # 確認條目
```

日誌：`~/.hermes/skills/harness-evolution/logs/run_fixes-YYYY-MM-DD.log`（保留 30 天）。

## 人工觸發（Hermes 主動呼叫）

當 CEO 說「巡檢一下」或「修一下服務綁定」時，Hermes 應：

1. 先跑 `run_fixes.sh --dry-run`，把診斷結果回報 CEO。
2. 破壞性或涉及重啟的項目，**先取得 CEO 批准**再跑完整修復。
3. 修復後把 curl 驗證輸出貼給 CEO（事實優先，不下結論式修飾）。

## 外循環演化掛載點（進階）

`src/` 下的 harness 專案可作為「候選腳手架」來源，但要上生產必須通過
`All-in/core/sesm_engine.py` 的 DGM 雙閘：

- 閘門 1（`validate`）：stages 只能取自 `ALLOWED_STATES`，且必須含 `TEST_STAGE` / `VERIFY_STAGE`
- 閘門 2（`verify_dgm`）：新版 `metrics.trials >= 20` 且 `success_rate >=` 現行版

任何繞過這兩道閘門的「自我改寫」，一律視為失敗並回滾。
